<h2>Exemplo Prático — Teste de API (Pagamento)</h2>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Validar endpoints de pagamento com cenários happy-path e erro.</li>
  <li>Escrever checks de contrato para payloads e status codes.</li>
  <li>Integrar testes de API simples no pipeline (localmente).</li>
</ul>

<h3>💡 Por que isso importa</h3>
<p>Validar a API garante que o frontend e serviços dependentes mantenham contrato estável sem precisar da interface gráfica.</p>

<h3>🔍 Exemplos de requisições</h3>
<pre>
POST /payments
{
  "userId": 1,
  "cardToken": "tok_abc",
  "amount": 150.00
}
</pre>

<h3>Checks essenciais</h3>
<ul>
  <li>200/201 para sucesso, 4xx para erro de validação, 5xx para erro do servidor.</li>
  <li>Payload de resposta contém `transactionId`, `status` e `amount`.</li>
  <li>Headers de segurança e rate-limit presentes.</li>
</ul>

<h3>📐 Contrato de request e response</h3>
<p>Antes de automatizar, defina o contrato mínimo. O teste deve validar regras observáveis, sem acoplar-se a campos internos que o consumidor não usa.</p>
<pre>{
  "request": {
    "userId": 1,
    "cardToken": "tok_abc",
    "amount": 150.00,
    "currency": "BRL",
    "idempotencyKey": "checkout-123-attempt-1"
  },
  "response": {
    "transactionId": "tx_123",
    "status": "approved",
    "amount": 150.00,
    "currency": "BRL"
  }
}</pre>
<ul>
  <li><strong>Tipos:</strong> <code>userId</code> é inteiro positivo; <code>amount</code> é número maior que zero; <code>currency</code> usa três letras.</li>
  <li><strong>Status:</strong> aceite apenas estados documentados, como <code>approved</code>, <code>pending</code> e <code>declined</code>.</li>
  <li><strong>Segurança:</strong> nunca envie número completo do cartão nem exponha token ou dados sensíveis na resposta.</li>
</ul>

<h3>🔁 Retry sem duplicar cobrança</h3>
<p>Retry não é repetir a requisição indiscriminadamente. Só repita erros transitórios, limite as tentativas e envie a mesma <code>idempotencyKey</code>. O provider deve devolver o mesmo resultado para a mesma chave, mesmo se a primeira resposta tiver sofrido timeout.</p>
<pre>async function postPayment(request, fetchImpl, maxAttempts = 3) {
  for (let attempt = 1; attempt &lt;= maxAttempts; attempt += 1) {
    const response = await fetchImpl('/payments', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Idempotency-Key': request.idempotencyKey,
      },
      body: JSON.stringify(request),
    });

    if (![502, 503, 504].includes(response.status) || attempt === maxAttempts) {
      return response;
    }

    await new Promise((resolve) =&gt; setTimeout(resolve, 100 * 2 ** (attempt - 1)));
  }
}</pre>
<p>Não faça retry automático em <code>400</code>, <code>401</code>, <code>402</code>, <code>403</code> ou <code>422</code>: a entrada ou autorização precisa ser corrigida, não repetida.</p>

<h3>✅ Teste resolvido com Playwright APIRequest</h3>
<p>O teste abaixo valida status, schema mínimo, valor e comportamento de idempotência. O endpoint e as credenciais devem vir de variáveis do ambiente, nunca de um arquivo versionado.</p>
<pre>const { test, expect } = require('@playwright/test');

test('creates a payment and preserves idempotency', async ({ request }) =&gt; {
  const payload = {
    userId: 1,
    cardToken: 'tok_test_approved',
    amount: 150.00,
    currency: 'BRL',
    idempotencyKey: `qa-${Date.now()}`,
  };

  const first = await request.post(`${process.env.PAYMENTS_URL}/payments`, {
    data: payload,
    headers: { 'Idempotency-Key': payload.idempotencyKey },
  });

  expect(first.status()).toBe(201);
  const body = await first.json();
  expect(body).toEqual(expect.objectContaining({
    transactionId: expect.any(String),
    status: expect.stringMatching(/approved|pending/),
    amount: payload.amount,
    currency: payload.currency,
  }));

  const second = await request.post(`${process.env.PAYMENTS_URL}/payments`, {
    data: payload,
    headers: { 'Idempotency-Key': payload.idempotencyKey },
  });

  expect(second.status()).toBe(201);
  expect((await second.json()).transactionId).toBe(body.transactionId);
});</pre>

<p>Para um teste determinístico de retry, use um mock ou ambiente de contrato que devolva 503 nas duas primeiras chamadas e 201 na terceira. Verifique que o cliente fez exatamente três chamadas e reutilizou a mesma chave.</p>

<h3>🧪 O que validar além do status code</h3>
<p>Um teste de API não termina no código HTTP. O QA também precisa checar se o corpo da resposta faz sentido, se os campos estão corretos e se o erro é tratado de forma previsível. Isso evita falsos positivos e melhora a confiança nos contratos.</p>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
{
  "transactionId": "tx_123",
  "status": "approved",
  "amount": 150.0
}
</pre>
<p>Em cenários de falha, a resposta deve indicar claramente o motivo e não expor detalhes internos desnecessários.</p>

  <li>Valide tempo de resposta e comportamento sob retry.</li>
  <li>Observe se o endpoint produz logs úteis para investigação.</li>
  <li>Teste tanto o fluxo feliz quanto os erros de validação e timeout.</li>
</ul>

<h3>📝 Exercício Prático</h3>
<ol>
  <li>Use `curl` ou Postman para enviar o POST acima contra uma API mock (Mockoon, WireMock ou servidor local).</li>
  <li>Escreva o schema mínimo de sucesso e três respostas de erro, incluindo status, <code>code</code> e mensagem segura.</li>
  <li>Implemente o teste Playwright de sucesso e idempotência, substituindo <code>PAYMENTS_URL</code> por um ambiente controlado.</li>
  <li>Simule duas respostas 503 seguidas de 201 e prove que o retry usa backoff, limite de tentativas e a mesma chave.</li>
  <li>Adicione um cenário 422 e confirme que ele não gera uma nova tentativa.</li>
</ol>

<h3>✅ Gabarito (exercício)</h3>
<ul>
  <li><strong>Validação com `curl`:</strong> o request deve retornar `200` ou `201` no happy-path e `4xx` para payload inválido. O QA deve confirmar também que `transactionId`, `status` e `amount` foram retornados no corpo.</li>
  <li><strong>Schema:</strong> sucesso contém <code>transactionId</code>, estado documentado, <code>amount</code> numérico igual ao request e moeda igual à enviada; erros contêm código e mensagem sem dados sensíveis.</li>
  <li><strong>Teste de API em Playwright:</strong> use <code>request.post()</code>, valide 201 e o corpo, repita a mesma chave e confirme o mesmo <code>transactionId</code>.</li>
  <li><strong>Retry:</strong> repita apenas 502/503/504, no máximo três vezes, com backoff crescente e a mesma chave; não repita 422.</li>
  <li><strong>Entregável mínimo:</strong> teste de sucesso, erro de validação, falha transitória e idempotência, com status, corpo e evidência das chamadas realizadas.</li>
</ul>
