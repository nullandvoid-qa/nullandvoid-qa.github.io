<h2>Exemplo Prático — Teste de API (Pagamento)</h2>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Validar endpoints de pagamento com cenários happy-path e erro.</li>
  <li>Escrever checks de contrato para payloads e status codes.</li>
  <li>Integrar testes de API simples no pipeline (localmente).</li>
</ul>

<h3>💡 Por que isso importa</h3>
<p>Validar a API garante que o frontend e serviços dependentes mantenham contrato estável sem precisar da interface gráfica.</p>

<h3>🔍 Exemplos de requisições</h3>
<pre>
POST /payments
{
  "userId": 1,
  "cardToken": "tok_abc",
  "amount": 150.00
}
</pre>

<h3>Checks essenciais</h3>
<ul>
  <li>200/201 para sucesso, 4xx para erro de validação, 5xx para erro do servidor.</li>
  <li>Payload de resposta contém `transactionId`, `status` e `amount`.</li>
  <li>Headers de segurança e rate-limit presentes.</li>
</ul>

<h3>🧪 O que validar além do status code</h3>
<p>Um teste de API não termina no código HTTP. O QA também precisa checar se o corpo da resposta faz sentido, se os campos estão corretos e se o erro é tratado de forma previsível. Isso evita falsos positivos e melhora a confiança nos contratos.</p>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
{
  "transactionId": "tx_123",
  "status": "approved",
  "amount": 150.0
}
</pre>
<p>Em cenários de falha, a resposta deve indicar claramente o motivo e não expor detalhes internos desnecessários.</p>

<h3>⚠️ Ponto de atenção</h3>
<ul>
  <li>Valide tempo de resposta e comportamento sob retry.</li>
  <li>Observe se o endpoint produz logs úteis para investigação.</li>
  <li>Teste tanto o fluxo feliz quanto os erros de validação e timeout.</li>
</ul>

<h3>📝 Exercício Prático</h3>
<ol>
  <li>Use `curl` ou Postman para enviar o POST acima contra uma API mock (ex: JSONPlaceholder ou Mockoon).</li>
  <li>Escreva um pequeno teste em Playwright (APIRequest) que valida status e schema.</li>
</ol>
