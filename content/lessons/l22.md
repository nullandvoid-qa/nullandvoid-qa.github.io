<h2>Lógica e POO para QA</h2>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Compreender fundamentos úteis de programação para automação de testes.</li>
  <li>Aplicar conceitos básicos de POO para organizar automação (Pages, Helpers, Models).</li>
  <li>Escrever funções pequenas e testáveis em JavaScript/TypeScript e Python.</li>
  <li>Transformar requisitos em código de validação simples e reutilizável.</li>
</ul>

<h3>🔍 Por que isso importa</h3>
<p>Mesmo que você não seja desenvolvedor, programar permite: automatizar passos repetitivos, validar regras com precisão, gerar massa de testes e integrar verificações em pipelines.</p>

<h3>⚙️ Conceitos essenciais</h3>
<ul>
  <li><strong>Variáveis e tipos:</strong> números, strings, booleanos, arrays e objetos.</li>
  <li><strong>Estruturas de controle:</strong> if/else, loops (for/while) e operadores lógicos.</li>
  <li><strong>Funções:</strong> organizar comportamento em unidades reutilizáveis.</li>
  <li><strong>POO (básico):</strong> classes, construtores, métodos, herança e encapsulamento — úteis para organizar pages, componentes e helpers.</li>
</ul>

<h3>🧩 Exemplo simples: validação de entrada (JavaScript)</h3>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
function isValidEmail(email) {
  if (!email || typeof email !== 'string') return false;
  return /^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email);
}

module.exports = { isValidEmail };
</pre>

<h3>🪜 Progressão de raciocínio para QA</h3>
<ol>
  <li><strong>Regra:</strong> escreva o comportamento em linguagem simples e defina entradas válidas, inválidas e limites.</li>
  <li><strong>Função pura:</strong> implemente uma função sem DOM, rede ou relógio para que o resultado dependa apenas da entrada.</li>
  <li><strong>Teste unitário:</strong> cubra classes de equivalência, bordas e erros esperados.</li>
  <li><strong>Integração:</strong> conecte a função ao storage, API ou componente e verifique o contrato entre módulos.</li>
  <li><strong>UI/E2E:</strong> valide somente o fluxo que precisa da interface; não repita todos os casos unitários na tela.</li>
</ol>

<h3>🧮 Exemplo completo: regra de carrinho</h3>
<p>Regra: o carrinho aceita itens com preço positivo e quantidade inteira entre 1 e 99. O subtotal é a soma de <code>price × quantity</code>; cupom <code>QA10</code> dá 10% de desconto quando o subtotal é pelo menos 100.</p>
<pre>function calculateCartTotal(items, coupon) {
  if (!Array.isArray(items)) throw new TypeError('items must be an array');

  const subtotal = items.reduce((total, item) =&gt; {
    if (!item || !Number.isFinite(item.price) || item.price &lt;= 0) {
      throw new Error('item price must be positive');
    }
    if (!Number.isInteger(item.quantity) || item.quantity &lt; 1 || item.quantity &gt; 99) {
      throw new Error('item quantity must be between 1 and 99');
    }
    return total + item.price * item.quantity;
  }, 0);

  const discount = coupon === 'QA10' &amp;&amp; subtotal &gt;= 100 ? subtotal * 0.1 : 0;
  return Number((subtotal - discount).toFixed(2));
}

module.exports = { calculateCartTotal };</pre>

<h3>🧪 Teste unitário resolvido (Jest)</h3>
<pre>const { calculateCartTotal } = require('./cart');

describe('calculateCartTotal', () =&gt; {
  test.each([
    [{ items: [], coupon: undefined, expected: 0 }],
    [{ items: [{ price: 25, quantity: 2 }], coupon: undefined, expected: 50 }],
    [{ items: [{ price: 60, quantity: 2 }], coupon: 'QA10', expected: 108 }],
  ])('$items with coupon $coupon returns $expected', ({ items, coupon, expected }) =&gt; {
    expect(calculateCartTotal(items, coupon)).toBe(expected);
  });

  test('rejects invalid price and quantity', () =&gt; {
    expect(() =&gt; calculateCartTotal([{ price: 0, quantity: 1 }])).toThrow(/price/);
    expect(() =&gt; calculateCartTotal([{ price: 10, quantity: 1.5 }])).toThrow(/quantity/);
    expect(() =&gt; calculateCartTotal([{ price: 10, quantity: 100 }])).toThrow(/quantity/);
  });
});</pre>
<p>O teste cobre uma classe vazia, um caso comum, o limite funcional do cupom e entradas inválidas. Se a regra mudar, o teste deve ser atualizado junto com o critério de aceitação, não receber um ajuste silencioso.</p>

<h3>🧭 Exemplo POO: Page Object (TypeScript)</h3>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
export class LoginPage {
  constructor(private page) {}

  async goto() { await this.page.goto('/login'); }
  async login(username: string, password: string) {
    await this.page.fill('#user', username);
    await this.page.fill('#pass', password);
    await this.page.click('button[type=submit]');
  }
}
</pre>

<h3>🧱 POO sem esconder o comportamento</h3>
<p>Um Page Object deve encapsular locators e ações de UI, mas não esconder decisões importantes do teste. Prefira métodos que expressem intenção e retornem dados verificáveis:</p>
<pre>export class CartPage {
  constructor(private page) {}

  async addItem(itemId: string) {
    await this.page.getByTestId(`add-${itemId}`).click();
  }

  async total(): Promise&lt;number&gt; {
    const text = await this.page.getByTestId('cart-total').innerText();
    return Number(text.replace('R$', '').replace(',', '.').trim());
  }

  async open() {
    await this.page.goto('/cart');
  }
}</pre>
<ul>
  <li><strong>Encapsulamento:</strong> o teste não repete seletores.</li>
  <li><strong>Composição:</strong> uma classe pode receber <code>LoginPage</code> ou um helper de API sem herança desnecessária.</li>
  <li><strong>Responsabilidade única:</strong> o Page Object interage com a tela; a regra de desconto fica em uma função/modelo testável.</li>
  <li><strong>Anti-padrão:</strong> não coloque todas as asserções, waits e regras de negócio em uma classe gigante.</li>
</ul>

<h3>🐍 Exemplo simples em Python (função testável)</h3>

def normalize_phone(phone: str) -> str:
    digits = ''.join(c for c in phone if c.isdigit())
    if len(digits) == 11:
        return f"+55{digits}"
    return digits

<h3>✅ Boas práticas para QA ao programar</h3>
<ul>
  <li>Escreva funções pequenas e com responsabilidade única (single responsibility).</li>
  <li>Separe lógica de seleção do DOM/elementos e lógica de verificação.</li>
  <li>Adote Page Objects ou helpers para evitar duplicação em testes UI.</li>
  <li>Escreva testes unitários para helpers críticos (validação de dados, conversões).</li>
  <li>Mantenha nomes claros para métodos e classes — isso facilita reprodução de bugs.</li>
</ul>

<h3>🧠 Regra de negócio em código</h3>
<p>Uma das melhores formas de dar valor como QA é transformar regras de negócio em pequenas funções e exemplos de teste. Quando uma regra está espalhada em vários pontos do fluxo, a chance de inconsistência cresce; por isso, concentrar a regra em um único ponto facilita manutenção e revisão.</p>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
function applyDiscount(total, customerType) {
  if (customerType === 'vip') return total * 0.9;
  if (customerType === 'new') return total * 0.95;
  return total;
}
</pre>
<p>Em testes automatizados, essa função pode ser validada com cenários claros de valor normal, desconto VIP e cliente novo.</p>

<h3>🧱 POO para organizar testes</h3>
<ul>
  <li><strong>Page Object:</strong> concentra seletores e interações com a tela.</li>
  <li><strong>Helpers:</strong> isolam lógica reutilizável como formatação, espera e conversão de dados.</li>
  <li><strong>Models:</strong> representam entidades do domínio e ajudam a testar regras sem depender de UI.</li>
</ul>
<p>Essa separação reduz duplicação e torna os testes mais fáceis de manter quando a interface muda.</p>

<h3>✅ Gabarito (exercício)</h3>
<ul>
  <li><strong>Validações para `isValidEmail`:</strong> `teste@qa.com`, `qa.user@empresa.org`, `nome+tag@dominio.io` devem ser válidos; `sem-arroba`, `@semnome`, `nome@`, `nome..sufixo@dominio.com` devem ser inválidos. Isso cobre casos reais de regra de negócio de e-mail.</li>
  <li><strong>Regra do carrinho:</strong> subtotal de 50 permanece 50; dois itens de 60 com <code>QA10</code> retornam 108; preço zero, quantidade fracionada ou quantidade 100 geram erro.</li>
  <li><strong>Teste progressivo:</strong> unitário cobre cálculo e limites; integração valida o formato entre carrinho e storage/API; E2E confirma somente o fluxo visual crítico.</li>
  <li><strong>Exemplo de `CartPage`:</strong> a classe concentra acesso ao DOM e expõe `addItem(itemId)` e `total()`, mas não decide o desconto. O teste verifica o total esperado após adicionar itens.</li>
  <li><strong>Helper reusável:</strong> extraia a validação do formulário para uma função com retorno booleano ou lista de mensagens de erro. Registre manualmente casos de UX e acessibilidade que não cabem na função.</li>
</ul>
