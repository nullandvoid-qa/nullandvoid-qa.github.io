<h2>Pirâmide de Testes e Estratégias de Automação</h2>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Entender a pirâmide de testes e como balancear testes unitários, integração e E2E.</li>
  <li>Conhecer alternativas modernas à pirâmide (torta, hockey-stick) e quando aplicá-las.</li>
  <li>Projetar uma estratégia de automação para reduzir flakiness e custo de manutenção.</li>
</ul>

<h3>💡 Contexto</h3>
<p>A pirâmide de testes é um guia para priorizar onde investir em automação: muitos testes rápidos e baratos na base (unit), menos testes caros no topo (E2E).</p>

<h3>📊 Visual (ASCII)</h3>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
        E2E (poucos, críticos)
       /------------------------\
      / Integration (média)     \
     /----------------------------\
    / Unit Tests (muitos, rápidos) \
   /--------------------------------\
</pre>

<h3>🧭 Boas práticas</h3>
<ul>
  <li><strong>Automatize lógica, não UI:</strong> prefira testar comportamentos e contratos em vez de testar estrutura de DOM volátil.</li>
  <li><strong>Use testes de contrato</strong> para desacoplar equipes (consumer-driven contracts).</li>
  <li><strong>Crie testes fiáveis:</strong> evite dependências externas, use mocks/fakes quando apropriado.</li>
  <li><strong>Pipeline:</strong> execute unit tests em commits, integração em PRs, E2E em nightly/merge para main.</li>
</ul>

<h3>⚠️ Anti-padrões comuns</h3>
<ul>
  <li><strong>Testar tudo via UI:</strong> testes E2E que exercitam detalhes de DOM para lógica simples tornam-se frágeis e lentos.</li>
  <li><strong>Mocks em excesso nos E2E:</strong> simular tudo no E2E cria falso sentimento de segurança.</li>
  <li><strong>Testes sem isolamento:</strong> dependência de estado compartilhado entre testes causa flakiness difícil de depurar.</li>
</ul>

<h3>🔁 Quando converter um E2E em Integração / Contrato</h3>
<ul>
  <li>Se o caso testa lógica de negócio (regras, transformações) sem depender de UI específica → mover para integração/unit.</li>
  <li>Se o caso valida comunicação entre serviços (API/consumer) e é determinístico → usar contract tests.</li>
  <li>Se o E2E é instável por detalhes de renderização mas a API garante a correção → converter para integração e manter um E2E leve de sanity-check.</li>
</ul>

<h3>📈 Matriz custo × risco (resumo)</h3>
<ul>
  <li><strong>Baixo custo / Alto risco:</strong> testes unitários para validação de lógica crítica (executam rápido, rodam em commits).</li>
  <li><strong>Médio custo / Médio risco:</strong> testes de integração que verificam contratos e integração entre módulos (rodar em PRs).</li>
  <li><strong>Alto custo / Baixo frequência:</strong> E2E para fluxos de ponta a ponta de alto impacto (rodar em main/nightly).</li>
</ul>

<h3>🔧 Política de retries e tratamento de flaky tests</h3>
<ul>
  <li>Retries automáticos: permitir 1 retry em E2E transientes; falha dupla = investigação humana.</li>
  <li>Marcar e isolar testes flaky: se um teste falha intermitentemente >3 vezes em 7 dias, movê-lo para investigação e não considerá-lo bloqueador no PR.</li>
  <li>Registrar evidências e criar ticket para estabilização: logs, screenshots, traces de rede e tempo de execução.</li>
</ul>

<h3>🔎 Exemplo aplicado ao projeto (sugestão)</h3>
<ul>
  <li><strong>Bookmark flow:</strong> converter de E2E para integração — validar lógica de armazenamento e sincronização com `app-bookmarks.js` por testes de integração que simulam o storage.</li>
  <li><strong>Quiz flow:</strong> manter E2E mínimos para leitura do fluxo completo, mas mover validações de regras de pontuação para testes unitários/integrados.</li>
  <li><strong>Checkout / Certificates:</strong> manter 2–3 E2E críticos (pagamento, emissão de certificado) e reduzir o restante a integração/contract tests.</li>
</ul>

<h3>🛠️ Exercício Prático</h3>
<ol>
  <li>Mapeie os testes existentes do projeto para a pirâmide (unit/integration/e2e).</li>
  <li>Identifique 3 casos E2E que podem ser convertidos em testes de integração ou contratos.</li>
  <li>Escreva um plano de execução para CI: quando rodar cada tipo de teste e políticas de retry.</li>
</ol>

<h3>✅ Gabarito (exercício)</h3>
<ul>
  <li><strong>Mapeamento da pirâmide:</strong> unitários para regras e helpers, integração para binding de estado e storage, E2E para fluxos de alto risco e baixa frequência.</li>
  <li><strong>Conversões candidatas:</strong> fluxo de bookmark, workflow de quiz e validação de formulário podem ser reduzidos para integração quando a UI é volátil ou o risco já está coberto por contrato.</li>
  <li><strong>Plano de CI:</strong> unit no push, integração em PR e E2E em merge/main ou nightly, com retries limitados e evidências de falha registradas.</li>
</ul>

<h3>🧪 Exemplo prático de pipeline</h3>
<p>Uma estratégia comum é:</p>
<ul>
  <li><strong>Unit:</strong> roda em todo push/PR para detectar regressões rapidamente.</li>
  <li><strong>Integration:</strong> roda em PRs ou nightly para validar contratos e fluxos principais.</li>
  <li><strong>E2E:</strong> roda em main ou release candidates, com artefatos e screenshots para investigar falhas.</li>
</ul>
