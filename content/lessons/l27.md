<h2>Testes de Contrato — Introdução e Pact</h2>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Entender o que são testes de contrato (consumer-driven contracts).</li>
  <li>Saber quando usar pactos/contract tests versus testes de integração.</li>
  <li>Gerar, publicar e verificar um contrato simples usando Pact (fluxo conceitual).</li>
</ul>

<h3>💡 Contexto</h3>
<p>Testes de contrato garantem que o contrato entre um consumidor (cliente) e um provedor (API) permaneça compatível. Eles são especialmente úteis quando equipes independentes desenvolvem serviços desacoplados.</p>

<h3>🔄 Consumer e provider: quem testa o quê?</h3>
<p>Num contrato orientado pelo consumidor, o <strong>consumer</strong> descreve apenas as interações de que precisa: método, rota, headers, parâmetros e o subconjunto do corpo que realmente utiliza. O Pact transforma essa expectativa em um arquivo versionado.</p>
<p>O <strong>provider</strong> executa suas rotas reais contra as interações do contrato. A verificação falha quando o provider muda um status, remove um campo obrigatório, altera um tipo ou deixa de aceitar a requisição esperada.</p>
<ol>
  <li>O consumer escreve uma expectativa contra um mock local do provider.</li>
  <li>O teste do consumer gera um pact file com as interações.</li>
  <li>O arquivo é publicado como artefato ou em um Pact Broker.</li>
  <li>O provider baixa o contrato e executa a verificação em CI.</li>
  <li>Uma mudança incompatível bloqueia o merge antes do deploy.</li>
</ol>

<h3>🧩 Exemplo executável com Node e Pact JS</h3>
<p>Crie um projeto de laboratório e instale a biblioteca:</p>
<pre>mkdir pact-lab
cd pact-lab
npm init -y
npm install --save-dev @pact-foundation/pact jest</pre>

<p>O consumer abaixo espera apenas o contrato que usa. O campo <code>currency</code> não é exigido porque não participa desta interação.</p>
<pre>const { PactV4, MatchersV3 } = require('@pact-foundation/pact');
const { like, integer, string } = MatchersV3;

describe('Orders API contract', () =&gt; {
  const provider = new PactV4({
    consumer: 'CheckoutWeb',
    provider: 'OrdersAPI',
    dir: './pacts',
  });

  test('gets an order summary', async () =&gt; {
    await provider
      .addInteraction()
      .given('order 123 exists')
      .uponReceiving('a request for order 123')
      .withRequest('GET', '/orders/123', (builder) =&gt; {
        builder.headers({ Accept: 'application/json' });
      })
      .willRespondWith(200, (builder) =&gt; {
        builder.headers({ 'Content-Type': 'application/json' });
        builder.jsonBody({
          id: integer(123),
          status: string('paid'),
          total: like(150.00),
        });
      })
      .executeTest(async (mockServer) =&gt; {
        const response = await fetch(`${mockServer.url}/orders/123`, {
          headers: { Accept: 'application/json' },
        });

        expect(response.status).toBe(200);
        expect(await response.json()).toEqual({
          id: expect.any(Number),
          status: expect.any(String),
          total: expect.any(Number),
        });
      });
  });
});</pre>

<p>Execute o teste e confirme que <code>pacts/CheckoutWeb-OrdersAPI.json</code> foi gerado:</p>
<pre>npx jest orders.consumer.test.js --runInBand
ls pacts</pre>

<h3>🛡️ Verificação no provider</h3>
<p>No pipeline do provider, a verificação deve subir a API em uma porta de teste e executar todas as interações publicadas. O exemplo abaixo usa o CLI do Pact como orientação de pipeline:</p>
<pre>npm install --save-dev @pact-foundation/pact

# API já iniciada em http://127.0.0.1:3000
npx pact-provider-verifier \
  ./pacts/CheckoutWeb-OrdersAPI.json \
  --provider-base-url=http://127.0.0.1:3000</pre>

<p>Em uma integração real, prefira o provider verifier oficial da linguagem/framework usado pelo serviço e configure o estado <code>order 123 exists</code> com fixture ou banco temporário. O ponto essencial é que cada estado declarado pelo consumer seja reproduzível no ambiente de verificação.</p>

<h3>🚦 O que é e não é quebra de contrato?</h3>
<ul>
  <li><strong>Compatível:</strong> adicionar um campo opcional que o consumer não exige.</li>
  <li><strong>Incompatível:</strong> trocar <code>status</code> de string para objeto ou remover <code>total</code>.</li>
  <li><strong>Incompatível:</strong> responder 204 quando o consumer espera 200 e um corpo JSON.</li>
  <li><strong>Risco contextual:</strong> restringir valores aceitos sem alterar o schema, por exemplo aceitar apenas <code>paid</code> quando o consumer também usa <code>pending</code>.</li>
</ul>

<h3>🧪 Exercício Prático</h3>
<ol>
  <li>Abra o template de contrato em <code>content/templates/contract-test-template.md</code> e transforme o exemplo de usuário em uma interação de pedidos.</li>
  <li>Escreva uma interação <code>GET /orders/123</code> com status 200, header JSON e os campos <code>id</code>, <code>status</code> e <code>total</code>.</li>
  <li>Defina o estado do provider: <code>order 123 exists</code>. Registre também o fixture usado para reproduzi-lo.</li>
  <li>Gere o pact file e descreva onde ele será publicado no CI.</li>
  <li>Simule uma quebra removendo <code>total</code> da resposta do provider. O teste deve falhar e explicar qual expectativa deixou de ser atendida.</li>
</ol>

<h3>✅ Gabarito (exercício)</h3>
<ul>
  <li><strong>Contrato mínimo:</strong> método <code>GET</code>, rota <code>/orders/123</code>, header <code>Accept: application/json</code>, status 200 e corpo com <code>id</code>, <code>status</code> e <code>total</code>.</li>
  <li><strong>Estado:</strong> o provider precisa preparar a fixture <code>order 123 exists</code> antes da verificação e removê-la ao finalizar o teste.</li>
  <li><strong>Publicação:</strong> o consumer publica o pact file com nome e versão identificáveis; o provider verifica essa versão no pipeline antes do deploy.</li>
  <li><strong>Falha esperada:</strong> se <code>total</code> for removido ou tiver tipo incompatível, a verificação deve falhar; isso é preferível a descobrir a quebra depois que o consumer já foi publicado.</li>
  <li><strong>Entrega de valor:</strong> o contrato reduz acoplamento de implementação, mas torna explícita a dependência comportamental que precisa ser preservada.</li>
</ul>
