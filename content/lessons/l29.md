<h2>Teste Exploratório, Relato de Bug e Critérios de Aceitação</h2>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Praticar testes exploratórios com charters e sessões time-boxed.</li>
  <li>Produzir relatos de bug completos e acionáveis.</li>
  <li>Gerar critérios de aceitação verificáveis a partir de um bug real.</li>
</ul>

<h3>💡 Contexto</h3>
<p>Testes exploratórios são uma prática essencial quando o produto evolui rápido ou quando existe risco não coberto por testes roteirizados. O objetivo desta aula é executar sessões curtas e produzir artefatos que possibilitem correção imediata e validação automática futura.</p>

<h3>🧭 Exploratory Charter (Preenchido — Exemplo)</h3>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
Goal: Verificar fluxo de checkout em mobile com cartão de crédito salvo
Timebox: 30 minutes
Setup:
 - Emulador Android 11, resolução 360x800
 - Usuário: user_test_checkout@example.com (senha: Test@123)
 - Rede: 4G (latency 80ms, bandwidth 5Mbps)
 - Massa: carrinho com 1 item SKU-abc-123, valor R$49,90
Areas to focus:
 - Seleção de cartão salvo e uso do CVV
 - Comportamento em falha de autorização (código 402)
 - Persistência do carrinho após erro
Notes: Capture vídeo curto para fluxo incompleto; registre timestamps e IDs de request
</pre>

<h3>📓 Sessão — Notas de Exemplo (time-boxed: 30m)</h3>
<ol>
  <li>00:00–02:00 — Setup e login com `user_test_checkout`.</li>
  <li>02:00–08:00 — Criar carrinho com SKU-abc-123; confirmar valor exibido.</li>
  <li>08:00–15:00 — Selecionar cartão salvo, inserir CVV; submeter pagamento.</li>
  <li>15:00 — Observação: resposta 500 do gateway após 2s; UI mostra spinner indefinido.</li>
  <li>16:00–22:00 — Repetir com rede instável (packet loss simulado); confirmar que carrinho não foi perdido.</li>
  <li>22:00–30:00 — Capturar evidências, coletar logs do browser, gravar vídeo de 30s do erro.</li>
</ol>

<h3>📝 Relato de Bug — Exemplo Completo (Bug 1)</h3>
<ul>
  <li><strong>Título:</strong> Checkout trava com spinner infinito quando gateway retorna 500</li>
  <li><strong>Passos para reproduzir:</strong>
    <ol>
      <li>Login com user_test_checkout@example.com</li>
      <li>Adicionar SKU-abc-123 ao carrinho</li>
      <li>Ir para checkout e selecionar cartão salvo</li>
      <li>Inserir CVV e submeter pagamento</li>
    </ol>
  </li>
  <li><strong>Resultado atual:</strong> Após envio, UI exibe spinner indefinido; requisição ao gateway retorna 500; usuário fica sem feedback e o botão permanece desabilitado.</li>
  <li><strong>Resultado esperado:</strong> Mostrar mensagem de erro clara ("Erro ao processar pagamento — tente novamente") e permitir re-tentativa sem perder o carrinho.</li>
  <li><strong>Evidências:</strong> video.mp4 (00:12–00:18), network HAR (checkout-har.json), console.log com stack trace X.</li>
  <li><strong>Ambiente:</strong> Emulador Android 11, app web v1.4.2, rede 4G simulado.</li>
  <li><strong>Severidade:</strong> Major — impede finalização de compra (impacto financeiro direto).</li>
  <li><strong>Prioridade:</strong> P0 — regressão crítica para fluxo de receita.</li>
  <li><strong>Hipótese de causa:</strong> Falha no tratamento de status 5xx do gateway; promessa não resolve nem rejeita, deixando estado UI preso.</li>
</ul>

<h3>📝 Relato de Bug — Exemplo Completo (Bug 2)</h3>
<ul>
  <li><strong>Título:</strong> Mensagem de erro de pagamento exibe texto genérico sem código de erro</li>
  <li><strong>Resumo:</strong> Quando o gateway retorna erro 402 (cartão recusado), a UI mostra "Erro" sem código ou instrução; usuários não sabem se devem tentar outro cartão.</li>
  <li><strong>Impacto:</strong> Usabilidade — aumenta desistência no checkout.</li>
  <li><strong>Evidências:</strong> screenshot-error-402.png; network response body com {"code":402,"reason":"card_declined"}.</li>
  <li><strong>Severidade:</strong> Medium — afeta conversão mas não bloqueia todas as compras.</li>
  <li><strong>Prioridade:</strong> P1 — corrigir para melhorar UX e reduzir churn.</li>
  <li><strong>Hipótese de causa:</strong> Mapeamento incompleto de códigos do gateway para mensagens amigáveis na camada frontend.</li>
</ul>

<h3>🔎 Severidade vs Prioridade (Guia rápido)</h3>
<ul>
  <li><strong>Severidade:</strong> medida técnica/funcional do impacto (Blocker, Major, Minor).</li>
  <li><strong>Prioridade:</strong> ordena correção com base em impacto de negócio, custo e esforço (P0, P1, P2).</li>
  <li>Exemplo: Bug que bloqueia checkout é Severidade=Blocker e tipicamente Prioridade=P0.</li>
</ul>

<h3>✅ Critérios de Aceitação — Ticket derivado (exemplo para Bug 1)</h3>
<ul>
  <li>Ao receber status 5xx do gateway, a UI exibe mensagem clara: "Erro do sistema de pagamento — tente novamente em alguns minutos".</li>
  <li>O botão de confirmação é reativado após 5s e o carrinho permanece intacto (itens + quantidades).</li>
  <li>Logs do servidor devem incluir requestId e status retornado; monitorar aumento de 5xx acima de baseline.</li>
  <li>Teste automático: simular 500 do gateway e verificar que a resposta do frontend contém a mensagem esperada e reativa o botão.</li>
</ul>

<h3>📚 Exercício Prático (atualizado)</h3>
<ol>
  <li>Forme duplas e execute 30 minutos de sessão exploratória usando o charter preenchido.</li>
  <li>Registre 2 bugs reproduzíveis com evidências (HAR, screenshot, vídeo) seguindo o template de bug.</li>
  <li>Escreva uma hipótese de causa para cada bug e mapeie a severidade/prioridade.</li>
  <li>Crie um ticket com critérios de aceitação testáveis (incluir teste automatizado de regressão se aplicável).</li>
</ol>

<h3>✅ Gabarito Verificável (exemplos esperados)</h3>
<ul>
  <li><strong>Bug 1 (esperado):</strong> título claro, passos numerados que reproduzem o spinner infinito, HAR anexado, vídeo demonstrando o bloqueio, severidade Major/Blocker, hipótese que indica tratamento assíncrono incompleto.</li>
  <li><strong>Ticket (esperado):</strong> critérios listados e um teste automatizado que simula 500 do gateway e valida a mensagem e reativação do botão.</li>
  <li><strong>Bug 2 (esperado):</strong> mostra mapping do código 402 para mensagem, screenshot e network response com body contendo {"code":402,"reason":"card_declined"}.</li>
</ul>

<h3>🧠 Dica prática para triagem</h3>
<p>Antes de abrir um ticket: verifique se o bug é reproduzível em outro ambiente, anexe evidências mínimas (passos + screenshot/har) e proponha uma hipótese curta — isso acelera a correção.</p>
