<h2>Exemplo Prático — CI/CD para QA (GitHub Actions)</h2>

<h2>CI/CD para QA — Exemplo Prático</h2>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Entender como executar testes de API e unitários no CI.</li>
  <li>Configurar um job simples no GitHub Actions para rodar `npm test`.</li>
  <li>Adicionar relatórios básicos e artefatos de teste.</li>
</ul>

<h3>💡 Por que isso importa</h3>
<p>Executar testes no pipeline evita regressões e entrega feedback rápido ao time antes do merge.</p>

<h3>🔧 Exemplo mínimo de workflow (GitHub Actions)</h3>
<pre>
name: CI
on: [push, pull_request]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: npm
      - name: Install dependencies
        run: npm ci
      - name: Lint
        run: npm run lint
      - name: Validate content
        run: npm run validate:all
      - name: Run smoke E2E
        run: npm run test:e2e:smoke
      - name: Upload coverage
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: jest-coverage
          path: coverage/
</pre>

<p>O arquivo acima é um gate básico: lint, validações editoriais e testes leves precisam passar para o job ficar verde. No repositório atual, o comando de validação completo é <code>npm run validate:all</code> e o smoke de E2E é <code>npm run test:e2e:smoke</code>. Isso mantém o exemplo alinhado aos scripts existentes, em vez de usar comandos não configurados como <code>npm run test:api</code> ou <code>npm run test:regression</code> antes de validá-los localmente.</p>

<p>Não use retry global para esconder instabilidade. Se a pipeline tem <code>retries: 2</code>, registre o teste como flakey e acompanhe a taxa de falha; retry é mitigação temporária, não aprovação automática.</p>

<h3>📦 Artefatos e investigação de falhas</h3>
<ul>
  <li><strong>Jest:</strong> publique <code>coverage/</code> para comparar cobertura e consultar o relatório HTML.</li>
  <li><strong>Playwright:</strong> preserve <code>playwright-report/</code>, screenshots, vídeos e traces somente quando houver falha para reduzir custo.</li>
  <li><strong>Logs:</strong> grave saída de validações e comandos de API com tokens e dados pessoais removidos.</li>
  <li><strong>Retenção:</strong> mantenha evidências de PR por período curto e resultados de release pelo período exigido pelo time.</li>
</ul>
<pre>- name: Run E2E smoke
  run: npm run test:e2e:smoke
- name: Upload Playwright evidence
  if: failure()
  uses: actions/upload-artifact@v4
  with:
    name: playwright-failure-${{ github.run_number }}
    path: |
      playwright-report/
      test-results/
    if-no-files-found: ignore</pre>

<h3>🔐 Gates, segredos e ambientes</h3>
<p>Credenciais de API devem ser configuradas em <code>Settings → Secrets and variables → Actions</code> e consumidas como variáveis de ambiente. Nunca coloque tokens, cartões de teste reais ou URLs privadas em fixtures versionadas.</p>
<pre>- name: API contract tests
  env:
    PAYMENTS_URL: ${{ secrets.PAYMENTS_URL }}
    PAYMENTS_TOKEN: ${{ secrets.PAYMENTS_TOKEN }}
  run: npm run test:api</pre>
<p>Se o projeto ainda não possui <code>test:api</code>, não invente um gate silencioso: adicione o script primeiro, teste-o localmente e só então o torne obrigatório.</p>

<h3>🔧 O que um pipeline de QA precisa fazer</h3>
<p>Um pipeline bem montado não existe apenas para “rodar testes”; ele deve entregar feedback rápido, registrar evidências e impedir que uma regressão passe para produção sem percepção do time. Para QA, o CI vira uma camada de proteção contínua.</p>
<ul>
  <li><strong>Feedback rápido:</strong> testes unitários e de integração no PR.</li>
  <li><strong>Evidência:</strong> logs, screenshots, relatórios e artefatos.</li>
  <li><strong>Segurança:</strong> bloqueio de merge quando um cenário crítico falha.</li>
</ul>

<h3>📦 Artefatos úteis</h3>
<ul>
  <li>Relatórios de cobertura e execução.</li>
  <li>Capturas de tela para failures de UI.</li>
  <li>Logs de API ou execução para investigação posterior.</li>
</ul>

<h3>📝 Exercício Prático</h3>
<ol>
  <li>Crie um arquivo <code>.github/workflows/ci.yml</code> usando Node 20, <code>npm ci</code>, lint, validações de conteúdo e testes unitários.</li>
  <li>Adicione o smoke E2E como gate de release e faça a suíte completa rodar apenas em <code>main</code> ou nightly.</li>
  <li>Publique cobertura sempre e evidências do Playwright apenas quando houver falha.</li>
  <li>Abra um PR e registre qual gate falhou, qual artefato foi consultado e qual decisão foi tomada.</li>
</ol>

<h3>✅ Gabarito (exercício)</h3>
<ul>
  <li><strong>Workflow:</strong> use <code>actions/checkout</code>, <code>actions/setup-node</code> com cache, <code>npm ci</code>, <code>npm run lint</code>, <code>npm run validate:all</code> e o teste E2E apropriado ao evento.</li>
  <li><strong>Gate:</strong> lint, conteúdo e unit/integration bloqueiam PR; smoke bloqueia release; a suíte completa pode ser nightly, mas deve gerar incidente ou tarefa quando falhar.</li>
  <li><strong>Artefatos:</strong> cobertura é publicada sempre; relatório, screenshot, vídeo e trace do Playwright são publicados quando falham.</li>
  <li><strong>Investigação:</strong> o relatório deve informar comando, ambiente, commit, teste falho e evidência suficiente para reproduzir.</li>
  <li><strong>Segurança:</strong> segredos entram por variáveis protegidas e não aparecem em logs, fixtures ou artefatos.</li>
</ul>
