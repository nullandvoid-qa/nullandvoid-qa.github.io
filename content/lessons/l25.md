<h2>Exemplo Prático — CI/CD para QA (GitHub Actions)</h2>

<h2>CI/CD para QA — Exemplo Prático</h3>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Entender como executar testes de API e unitários no CI.</li>
  <li>Configurar um job simples no GitHub Actions para rodar `npm test`.</li>
  <li>Adicionar relatorios básicos e artefatos de teste.</li>
</ul>

<h3>💡 Por que isso importa</h3>
<p>Executar testes no pipeline evita regressões e entrega feedback rápido ao time antes do merge.</p>

<h3>🔧 Exemplo mínimo de workflow (GitHub Actions)</h3>
<pre>
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '18'
      - name: Install
        run: npm ci
      - name: Run tests
        run: npm test -- --runInBand
</pre>

<h3>🔧 O que um pipeline de QA precisa fazer</h3>
<p>Um pipeline bem montado não existe apenas para “rodar testes”; ele deve entregar feedback rápido, registrar evidências e impedir que uma regressão passe para produção sem percepção do time. Para QA, o CI vira uma camada de proteção contínua.</p>
<ul>
  <li><strong>Feedback rápido:</strong> testes unitários e de integração no PR.</li>
  <li><strong>Evidência:</strong> logs, screenshots, relatórios e artefatos.</li>
  <li><strong>Segurança:</strong> bloqueio de merge quando um cenário crítico falha.</li>
</ul>

<h3>📦 Artefatos úteis</h3>
<ul>
  <li>Relatórios de cobertura e execução.</li>
  <li>Capturas de tela para failures de UI.</li>
  <li>Logs de API ou execução para investigação posterior.</li>
</ul>

<h3>📝 Exercício Prático</h3>
<ol>
  <li>Crie um arquivo `.github/workflows/ci.yml` com o workflow acima.</li>
  <li>Abra um PR e verifique se o job de `test` roda e retorna um status.</li>
  <li>Adicione um passo simples para publicar um artefato de log ou relatório.</li>
</ol>
