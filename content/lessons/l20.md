<h2>CI/CD para QA</h2>

<h3>🎯 Objetivos de Aprendizado</h3>
<ul>
  <li>Entender por que QA precisa conhecer CI/CD.</li>
  <li>Ver como Jenkins e GitHub Actions são usados para executar testes automaticamente.</li>
  <li>Aprender o conceito de quality gates e shift-left testing.</li>
  <li>Montar um pipeline simples que roda testes de API e regressão.</li>
</ul>

<h3>🔍 Por que isso importa</h3>
<p>O QA moderno não entrega apenas testes manuais. Ele garante que os testes rodem automaticamente em cada mudança e que o feedback chegue rápido ao time.</p>

<ul>
  <li><strong>Automação contínua:</strong> testes são executados a cada pull request ou merge.</li>
  <li><strong>Feedback rápido:</strong> problemas aparecem antes da entrega em produção.</li>
  <li><strong>Qualidade mensurável:</strong> testes com status e relatórios tornam o processo mais confiável.</li>
</ul>

<h3>Conceitos-chave</h3>
<ul>
  <li><strong>Pipeline:</strong> sequência de etapas que construem, testam e liberam o software.</li>
  <li><strong>Job:</strong> tarefa específica como `build`, `test` ou `deploy`.</li>
  <li><strong>Trigger:</strong> evento que dispara o pipeline (`push`, `pull_request`, agendamento).</li>
  <li><strong>Quality gate:</strong> conjunto de critérios que devem ser atendidos para permitir o merge.</li>
</ul>

<h3>Exemplo GitHub Actions</h3>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
name: QA Pipeline

on:
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'
      - name: Install dependencies
        run: npm ci
      - name: Run project validations
        run: npm run validate:all
      - name: Run smoke tests
        run: npm run test:e2e:smoke
</pre>
<p>No workflow real deste projeto, o comando de validação completo é <code>npm run validate:all</code>, que inclui lint, validações de trilhas, lições, links, catálogo e i18n. A smoke suite leve é executada com <code>npm run test:e2e:smoke</code>. Isso evita dependências de comandos inventados sem ciclo de teste, como <code>npm run test:api</code> ou <code>npm run test:regression</code>, até que estejam configurados e validados localmente.</p>

<h3>Exemplo Jenkins</h3>
<p>Jenkins também é muito usado em grandes empresas e permite orquestrar pipelines mais complexos.</p>
<pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">
pipeline {
  agent any
  stages {
    stage('Checkout') {
      steps {
        checkout scm
      }
    }
    stage('Install') {
      steps {
        sh 'npm install'
      }
    }
    stage('API Tests') {
      steps {
        sh 'npm run test:api'
      }
    }
    stage('Regression Tests') {
      steps {
        sh 'npm run test:regression'
      }
    }
  }
}
</pre>

<h3>Pipeline ideal para QA</h3>
<p>Um pipeline útil para QA não precisa ser complexo desde o início. O ideal é separar etapas por valor: build, testes de API, testes de regressão e relatórios claros.</p>
<ul>
  <li><strong>Stage 1:</strong> instalação de dependências e validação de ambiente.</li>
  <li><strong>Stage 2:</strong> testes de API e contrato.</li>
  <li><strong>Stage 3:</strong> testes de regressão ou smoke tests críticos.</li>
  <li><strong>Stage 4:</strong> publicação de relatórios e bloqueio de merge em caso de falhas críticas.</li>
</ul>

<h3>🛠️ Como depurar uma falha no pipeline</h3>
<p>Quando um teste falha no CI, o papel do QA é ir além de dizer “falhou”. O ideal é identificar se a falha é de ambiente, de teste, de regressão ou de comportamento real.</p>
<ul>
  <li>Verifique os logs da etapa que falhou e busque mensagens de erro claras.</li>
  <li>Compare o commit com a última execução estável.</li>
  <li>Reproduza o cenário localmente para confirmar se o problema é real ou falso positivo.</li>
  <li>Baixe os artefatos do pipeline, como relatórios HTML ou XML, para investigar melhor.</li>
</ul>

<p>Em muitos times, uma falha de pipeline vira um ticket de investigação, não apenas de execução. Isso melhora a qualidade do processo e reduz retrabalho.</p>

<h3>📣 Notificações e alertas</h3>
<p>Também é comum conectar o pipeline a canais de comunicação para que o time saiba rapidamente quando algo quebra.</p>
<ul>
  <li>Slack ou Teams podem receber alertas de falha em PRs e builds críticos.</li>
  <li>O QA pode definir gatilhos para notificar apenas em regressões de alto impacto.</li>
  <li>O objetivo é reduzir tempo de resposta e deixar o processo mais transparente.</li>
</ul>

<h3>Quality gates práticos</h3>
<p>Um good gate não precisa ser enorme. O mais útil costuma ser simples e objetivo:</p>
<ul>
  <li>Os testes críticos precisam passar antes do merge.</li>
  <li>Falhas de API ou regressão crítica devem bloquear a entrega.</li>
  <li>Relatórios devem mostrar claramente o que falhou, onde e com que severidade.</li>
</ul>
<p>Se o pipeline pode dizer “isso passou” ou “isso não passou” em minutos, o time ganha velocidade sem perder rastreabilidade.</p>

<h3>O papel de QA no pipeline</h3>
<ul>
  <li>Definir quais suites de teste devem ser executadas automaticamente.</li>
  <li>Escolher gatilhos de CI para validação de PRs e builds principais.</li>
  <li>Revisar resultados de testes e relatórios de falha.</li>
  <li>Manter o pipeline estável e remover testes obsoletos ou instáveis.</li>
</ul>

<h3>Quality gates</h3>
<p>Quality gates são critérios que impedem a entrega quando algo está errado.</p>
<ul>
  <li>Todos os testes críticos passam.</li>
  <li>Cobertura mínima obrigatória para áreas críticas.</li>
  <li>Sem regressões conhecidas em funcionalidades essenciais.</li>
  <li>Relatórios de falhas devem ser analisados antes do merge.</li>
</ul>

<h3>✅ Gabarito (exercício)</h3>
<ul>
  <li><strong>Fluxo de CI/CD sugerido:</strong> commit → build → lint → testes de API → testes de UI → relatórios → deploy em staging. Isso cobre validação rápida e escalonada antes de qualquer entrega.</li>
  <li><strong>YAML básico de GitHub Actions:</strong>
    <pre style="background:#f5f5f5; padding:1rem; border-radius:0.5rem; overflow-x:auto">name: API Tests

on:
  pull_request:
    branches:
      - main

jobs:
  api-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'
      - name: Install dependencies
        run: npm install
      - name: Run API tests
        run: npm test -- --runInBand --testPathPattern=api
</pre>
    </li>
  <li><strong>Quality gates recomendados:</strong>
    <ul>
      <li>Todos os testes críticos de API e UI devem passar.</li>
      <li>Sem regressões em fluxos essenciais identificadas pelo relatório de falhas.</li>
      <li>Cobertura mínima de testes para áreas críticas ou release candidate aprovada.</li>
    </ul>
  </li>
</ul>
